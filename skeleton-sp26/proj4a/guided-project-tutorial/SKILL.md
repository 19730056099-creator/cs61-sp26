# 渐进式项目实操教程

## 目标

让读者始终能回答：

> 我现在在哪 → 这一步要解决什么 → 改哪个文件哪里 → 放什么代码 → 为什么这样改 → 怎么证明成功。

写成带路的操作手册，而不是把完整答案、概念词典和后续课程装进同一篇说明书。目标是帮助读者最后能独立实现相似功能，不只是复制后运行。

默认用中文叙述，代码保留项目原有语言与命名。

## 1. 从已有上下文确定任务，不重复采访

优先从对话、参考教程和项目中提取：

- 读者当前水平、卡住的位置、已经学过什么。
- 当前代码版本、目标功能或目标版本。
- 希望一次性得到文档，还是一次只做一步。
- 是否允许改源码、执行程序、产生测试文件。
- 输出路径、已有教程能否覆盖。

已经明确的内容不再追问。只有起点、目标或权限缺失到会影响教程正确性时，问一个聚焦的问题。

用户给了参考文档时，先阅读，再提炼它的组织方式。复用“明确位置、具体动作、验证反馈”等方法，不照搬其中的业务细节、错误实现、个人路径或凭据。

## 2. 查清真实起点

在编写修改步骤前，检查与任务直接相关的：

1. 项目约束与局部说明。
2. 入口、待完成方法、相关调用链。
3. 构建方式、依赖、测试目录、运行工作目录。
4. 代表性输入数据及实际格式。
5. 如果涉及版本升级，比较当前与目标的相关文件。
6. 必要时读取官方要求；区分课程要求与自己的教学选择。

用一张简短的起点表说明：

| 部分 | 当前状态 | 谁来完成 |
|---|---|---|
| 框架或显示层 | 已提供 | 暂时使用，不研究实现 |
| 核心逻辑 | 缺少哪些具体行为 | 本教程逐步完成 |
| 数据与配置 | 是否齐全、如何定位 | 保留用户本地设置 |

不要猜测文件中“应该有”的代码，也不要将旧版本的测试数、路径和验证结论直接沿用到新版本。

## 3. 用可见成果拆步骤

先列阶段表：每行包含阶段目标、可观察结果、涉及文件。阶段名称优先写“让演示图显示出来”，而不是“理解抽象与多态”。

优先建立这样的学习节奏：

```text
跑通现成示例或复现小问题
→ 修好一个最小行为
→ 验证底层逻辑
→ 换成真实数据
→ 组合已有方法
→ 接入界面或外部系统
→ 完整验收
→ 总结与迁移
```

按依赖组织，保持每一步尽量可编译。没有独立运行入口的阶段，明确只做编译检查，并指出哪一步首次验证行为；不要假装重启未接线的程序就测试到了新代码。

一小步只承担一个主要目标。目标不可再拆时，允许多个必要改动；若一次引入多个陌生概念，重新拆步骤。

## 4. 使用固定的步骤结构

编写教程前读取 `references/tutorial-template.md`，按任务删减，不机械填满空章节。

每步遵循：

1. **目标与现象**：一个具体问题或输入输出例子。
2. **修改前的检查**：需要时先给小测试或复现命令。
3. **精确修改**：路径、定位锚点、动作、完整修改单元。
4. **就地解释**：只解释这一段用到的知识。
5. **验证**：操作、预期、尚未完成的部分、失败时检查哪里。
6. **思考题**：围绕刚完成的行为，问题少而具体。

新术语在真正用到时才出现，先说普通话，再补名称。例如先解释“把已创建的数据对象传给处理器”，之后才标注“构造器依赖注入”。

区分三类知识：

- **本步必须理解**：核心逻辑与数据关系。
- **现在会用即可**：框架接口、编码器、文件读取调用。
- **以后再学**：后续项目算法、优化或复杂架构。

降低前置负担，但不要把真正必需的先修知识藏起来。后续需要图遍历时，明确 A 的 Map 练习不能代替 DFS/BFS。

## 5. 代码必须能照着改

### 明确动作与范围

- 写清“新增文件”“增加 import”“在字段区加入”“替换整个方法”“仅替换这一行”“删除无用导入”。
- 定位用类名、方法签名、已有语句等稳定锚点，行号只作辅助。
- 新文件给 package、imports 和完整类；替换方法给签名及完整方法体。
- 相同名称的重载方法，用参数签名区分。
- 说明方法片段不是完整文件；避免读者覆盖整个文件或嵌套粘贴方法。
- 应用代码块内部不留省略号；伪代码和示意片段明确标注，不能混作可执行修改。
- 避免依赖后文尚未创建的类型或方法，尤其注意测试的 imports。

### 保持项目边界

- 用户只要教程时，只写教程及获准的配套资源，不改源码。
- 验证优先使用临时副本，不把实验改动写回工作区。
- 保留本地配置、用户已有工作及明确禁止修改的代码。
- 不自动提交、推送、安装依赖、改凭据或启动长期服务。
- 不为了复制某个课堂版本而让读者故意引入已知错误；需要讲错误时，使用隔离反例并立即解释。
- 不给真实凭据、无关个人路径或无授权外部副作用作为教程操作。
- 正式课程任务提示适用的提交限制，不把参考代码说成可直接提交的保证答案。

### 优先清楚，不炫技

使用与读者水平和项目风格相符的实现。先完成正确的简单版，确有必要再介绍优化。

如果使用未见过的 API，在旁边解释参数、返回值与作用。不要为简短而同时引入一串 Stream、lambda、工厂和设计模式。

## 6. 让验证和当前阶段匹配

分别标明：

- **操作**：哪个测试方法、命令或页面动作。
- **预期**：结果是什么，包含顺序、格式、边界等要求。
- **范围**：现在只通过哪些测试，哪些功能仍未实现。
- **故障入口**：失败时先查文件、配置、数据还是接线。

核心逻辑优先小样本和单元测试，最后再做完整系统验收。不要用“出现了一张图”代替数据正确性验证。

测试代码要与生产代码同样精确：新增到哪个文件、哪个类里，何时解除注释，是否需要 imports。先展示期望行为和失败检查，再给实现；未经实际执行，不声称已经看到了失败或通过。

如果有执行权限与工具：

1. 在临时目录还原起点。
2. 按教程顺序逐阶段应用代码，而不只验证最终合并版本。
3. 阶段内编译，运行已完成部分的相关测试。
4. 最后运行完整可见测试，必要时测试界面/接口。
5. 停止本次启动的进程，清理临时资源。
6. 报告实际执行方式、结果、警告和未覆盖部分。

不能执行时，报告“静态检查/未运行”，并给读者明确的验证操作。代码编译成功、单元测试通过、浏览器端到端通过和隐藏测评通过是不同结论，不混用。

## 7. 将总结和后续内容放在末尾

先完成当前项目，再用少量问题提炼知识：

- 为什么选这个结构？
- 哪些对象会被修改，哪些结果必须是副本？
- 哪些操作只在初始化做，哪些每次查询做？
- 能否合上答案重写一个关键方法？

思考题围绕反事实、边界和迁移，不提前考尚未讲解的名词。附简短答案提示，或集中到末尾，避免把每题扩展成新章节。

后续项目只给：

1. 与当前项目相同和不同的能力。
2. 真正新增的先修知识。
3. 小型纸笔例子与常见语义坑。
4. 独立实现顺序与最小测试清单。
5. 判断能否独立继续的标准。

用户要独立完成后续部分时，不直接塞入后续整套答案，也不承诺“学完必定速通”。

## 8. 交付前检查

- [ ] 起点来自实际读取，必要假设已标明。
- [ ] 每步目标可观察，修改位置和单位明确。
- [ ] 新增代码引用的类型/方法在该阶段已存在。
- [ ] imports、包名、构建与工作目录无缺口。
- [ ] 不把待删除代码块误算成要插入的代码。
- [ ] 每步只解释当前需要的知识，后续内容放末尾。
- [ ] 验证覆盖实际行为，不误称全部测试应提前通过。
- [ ] 保留用户配置和源码边界，没有未经授权的操作。
- [ ] 没有保留已知错误让读者照抄。
- [ ] 验证记录与本版一致，未测试项目如实说明。
- [ ] 思考题有针对性，读者有闭卷重写或纸笔练习机会。

## 配套资源

- `references/tutorial-template.md`：写新教程时读取，提供整体结构、单步格式和短示范。
- `evals/evals.json`：修改本 skill 时用于回归检查的 3 个测试任务。它们是待执行的测试用例，不是已经通过的评测报告。

默认输出用户指定位置的一份 Markdown 教程。结尾简短提供路径、已做验证与源码是否改动，不在聊天里再重复整份文档。
